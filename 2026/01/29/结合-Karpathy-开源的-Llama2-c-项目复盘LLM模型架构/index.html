结合 Karpathy 开源的 Llama2.c 项目复盘LLM模型架构

Karpathy 开源的 Llama2.c 项目是揭秘 LLM 模型架构组成及推理优化技术的窗口。本文以一次“把 HF 模型导出为 llama2.c 可读的 .bin”为线索，用 Debug 的方式复盘了 LLM 模型的架构组成。

为什么要 Debug export.py？

Karpathy 的 llama2.c 项目目标很明确：用尽可能少的依赖，在 C 里跑一个 LLaMA2 推理。要做到这一点，最先解决的问题不是推理，而是权重格式——C 程序并不能理解 HuggingFace 的各种 checkpoint 组织方式，它更希望拿到一个“按固定顺序排列的二进制文件”，读完就能把指针指到对应权重上。

因此 export.py 的角色是：
把符合 LLaMA2 架构的 HF 模型 → 导出为一个布局固定的 .bin 文件。

本次选择的导出对象是：

该模型的关键配置如下（Debug 时需确认一致）：

  • dim=768
  • n_layers=12
  • n_heads=12
  • n_kv_heads=12
  • hidden_dim=2268
  • vocab_size=32000
  • max_seq_len=1024
  • shared_classifier=True（embedding 与 output 权重共享）

Debug 的方法：用 out_file.tell() + shape/numel 验证二进制协议

在 legacy_export() 里，每写完一段内容，文件大小都会增长。可以用两件事来验证：

  1. out_file.tell()：当前写入位置（单位是 bytes，不是 bits）
  2. 每段权重的 shape → numel() → 增量 bytes；增量(bytes) = numel * 4（因为 serialize_fp32() 会把张量转成 fp32 再写出）

即使模型权重在内存里是 fp16/bf16（2 bytes），legacy_export 仍会 to(float32)，所以落盘一定按 4 bytes/元素计算。

Step 1：Header（7 个 int32）

legacy_export() 的起点是写入 header（7 个 int32）。
我们在写完 header 后验证：

  • 7 个值分别是：768, 2268, 12, 12, 12, 32000, 1024
  • out_file.tell() == 28（= 7 * 4 bytes）

这一步的意义：

  • .bin 文件在字节层面声明了“我是谁”（模型结构参数）
  • C 端 loader 只要先读这 28 bytes，就能知道后面要读多少层、每层矩阵多大、RoPE 表多长

Step 2：Embedding（tok_embeddings）

紧接着写 tok_embeddings.weight，其 shape 为 (32000, 768)：

  • numel = 32000 * 768 = 24,576,000
  • 写入增量 = 24,576,000 * 4 = 98,304,000 bytes
  • 写完后 out_file.tell() = 28 + 98,304,000 = 98,304,028

这一步把“vocab_size 和 dim”变成了一个真实的大矩阵：
词表行数 = 32000；每个 token 的 embedding 向量长度 = 768。

Step 3：逐块写入各层权重（关键：不是“逐层”，而是“逐权重块”）

值得注意的是，导出顺序是：先写完所有层的 attention_norm，再写完所有层的 wq，再写 wk…

因此 Debug 的正确姿势是：每个块只验证一两次（第 0 层），确认单次增量，然后用 Continue 让它跑完 12 层。

下面按 Debug 中走过的顺序复盘每个组件的“shape 与增量”。

attention_norm（12 次，每层一个向量）

  • 单层增量：768 * 4 = 3,072
  • 12 层总增量：3,072 * 12 = 36,864

在 Debug 中看到每次 F10 写完，tell() 增加 3072，这就等价于“又写完一层 norm”。

attention.wq / wk / wv / wo（12 次，每层一个 768×768）

每个权重矩阵的 shape 都是 (768, 768)：

  • 单层 numel = 768*768 = 589,824
  • 单层增量：589,824*4 = 2,359,296
  • 12 层总增量：2,359,296*12 = 28,311,552

四个矩阵（Q/K/V/O）合计：
28,311,552 * 4 = 113,246,208 bytes

这一步非常直观地把 Transformer 的注意力层拆成了传统线代：
四个线性层矩阵决定了 Q/K/V 的投影和输出投影。

ffn_norm（12 次，每层一个向量）

  • 单层：3,072
  • 12 层：36,864

FFN：feed_forward.w1 / w2 / w3

在Debug过程中观察到 w1.shape = (2268, 768)，这就是 FFN 的中间维度 hidden_dim=2268 在落地。

w1: (2268, 768)

  • 单层 numel = 2268*768 = 1,741,824
  • 单层增量：1,741,824*4 = 6,967,296
  • 12 层总增量：6,967,296*12 = 83,607,552

w2: 通常是 (768, 2268)

  • 单层 numel 同样是 768*2268 = 1,741,824
  • 12 层总增量同样是 83,607,552

w3: 通常也是 (2268, 768)

  • 同 w1：83,607,552

FFN 三块合计：

  • 83,607,552 * 3 = 250,822,656 bytes

这段 Debug 让人很“具象”地感受到：
在很多 LLM 里，FFN 的参数量和计算量往往比 attention 更大。

final rmsnorm（只写一次）

  • 增量：768*4 = 3,072

它是“所有层结束后”的最终归一化，属于模型尾部的一次性参数。

RoPE：freqs_cos / freqs_sin（你观察到 shape = 1024×32）

该步骤可以观察到：

  • model.freqs_cos[:p.max_seq_len].shape = (1024, 32)
  • model.freqs_sin[:p.max_seq_len].shape = (1024, 32)

为什么是 32？
因为 head_dim = dim/n_heads = 768/12 = 64，RoPE 以“成对旋转维度”存表，通常是 head_dim/2 = 32。

每张表的写入：

  • numel = 1024*32 = 32,768
  • 增量：32,768*4 = 131,072 bytes
    两张表合计：262,144 bytes

final classifier weights：要不要写？

代码里有：

Debug 得到 shared_classifier=True，所以 不会写 output.weight。
这点非常关键，因为它会直接影响 .bin 的尾部布局与最终大小。

终局验收：tell() 与文件大小一致

最后在 close 前：

  • out_file.tell() = 462,711,836

落盘后：

  • ls -l 显示 .bin 文件大小 也正好是 462,711,836 bytes

这一步相当于做了一个“格式闭环验收”：
导出流程写出的字节数 = 文件真实大小，没有少写、多写或错写 dtype 导致的偏差。

Debug 的“工程收获”：到底学到了什么？

把今天的 Debug 体验总结成一句话： Transformer 直观地变成了“可用偏移量验证的二进制协议”。

具体体现在：

  • 模型结构参数（dim/layers/heads/hidden_dim/seq_len）是写进 header 的硬约束
  • 每个组件（Norm / Attention / FFN / RoPE）都对应一段可计算的 numel*4 字节增量
  • .bin 的读写顺序是一种“契约”：写端怎么排，读端就必须怎么读；Debug 是把契约讲清楚的最快方式

附：在 VSCode/WSL 里有用的 Debug 小技巧

  • 断点要下在函数体可执行行
  • 循环很多时：给断点设置 Hit Count=1，只停第一层做验证
  • 用 Debug Console 记录块级增量：
    • start = out_file.tell() → 跑到下一个块 → out_file.tell()-start
  • 永远记住：out_file.tell() 单位是 bytes
